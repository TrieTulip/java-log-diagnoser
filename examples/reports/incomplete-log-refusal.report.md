# 诊断报告：信息不足，拒绝盲目诊断

> 日志来源：`examples/logs/incomplete-log-refusal.log` · 分析行数：1（共 1 行） · 分析工具：java-log-diagnoser
> 脚本结论：`exception_count=0`、`chain_count=0`、`frame_count=0`、`error_lines=1`
> 降级原因：全日志只有一行 ERROR 文本，没有异常类型、没有 `at` 帧、没有 `Caused by`，
> 也没有线程名、traceId 与应用名

**结论：无法定位。** 这段日志只够确认"某个时刻记录过一次 ERROR"，不足以支持任何根因判断；
按红线 R3 拒诊，下面是缺口与补齐方式。

## 1. 已知

- 日志只有一行（L1，逐字引用）：

  > 2023-10-27 10:00:00 ERROR - something went wrong, please check the database.

- 这一行能确认的只有三件事：时间 `2023-10-27 10:00:00`、级别 `ERROR`、文案里出现了
  `database` 这个词。
- 它**不能**确认：哪个类或方法抛的、抛的是什么、有没有内层原因、影响的是哪个请求。
  脚本的 `warnings` 原文也说明了这一点：`未在日志中解析到异常堆栈：可能只有一行错误文本，或日志格式非标准。`

## 2. 为什么不够

- **没有异常类型**：连"是空指针、超时、还是业务校验失败"都无法区分，而这四类问题的排查方向完全不同。
- **没有 `at` 帧**：无法定位到任何一个代码行，任何"某处未判空/未捕获"的说法都只能是想像。
- **没有 `Caused by`**：外层现象与内层原因无法分离——这次 ERROR 可能本身就是最外层，也可能只是某次重试的尾巴。
- **`database` 只是一个单词**：它可能指连接池、SQL、权限、网络，甚至只是日志作者的随手提示。
  在拿到实际异常前，把这四种方向排成优先级，等于用猜测替代排查。

因此本报告**不输出根因假设，也不输出修复建议**。

## 3. 需要你补充（按优先级）

1. **该 ERROR 前后各 50 行的上下文日志**：包含线程名、traceId、应用名，以及同一时刻的其它
   WARN/ERROR。目的是判断这一行是链路的起点还是终点。
2. **完整的异常堆栈**：从异常类名那一行开始，到最后一条 `at` 帧，含全部 `Caused by`。
   如果堆栈是被日志框架吞掉的，请一并给出该框架的异常打印配置。
3. **数据库连接配置（去掉密码）**：连接串、连接池上限与获取超时、是否开启自动重连；
   以及同一时段数据库侧的活跃连接数与慢查询记录。

## 4. 你可以先做的只读检查

| 目的 | 命令 | 期望观察 |
| --- | --- | --- |
| 找到这行前后发生了什么 | `grep -n -C 50 "something went wrong" </path/to/app.log>` | 前后是否紧跟着堆栈、重试记录或其它组件的同时报错 |
| 确认是否有同 traceId 的链路 | `grep -n "<traceId>" </path/to/app.log> \| head -50` | 请求能否被串起来；若为空，说明这行日志根本没打 traceId |
| 看同时间段连接层是否报错 | `grep -c "Connection is not available\|Communications link failure" </path/to/app.log>` | 计数为 0 说明问题可能不在连接层，别在数据库上耗时间 |
| 确认日志有没有被采集环节截断 | `wc -l </path/to/app.log>`，与采集端条数对比 | 条数明显偏少，说明堆栈可能在采集侧就被丢掉了 |

`<path>` 为应用日志路径，`<traceId>` 取该请求的链路 ID——两者都需要你从环境里取，不要用占位符直接执行。

## 5. 补齐之后我会怎么分析

拿到堆栈后按这个顺序推进，不需要你重复描述现象：

1. 重跑脚本，取主链与最深的业务帧；
2. 若最深 `Caused by` 是连接/超时类异常 → 转数据库侧可用性与连接池参数；
3. 若是业务异常被包装成通用 ERROR → 转业务规则与错误码语义；
4. 若堆栈仍然缺失 → 建议在抛异常处保留原始异常（`log.error("...", e)`），而不是只打 `e.getMessage()`。
