# 诊断报告：信息不足，拒绝盲目诊断

> 日志来源：`examples/logs/insufficient-info.log` · 分析行数：4（共 4 行） · 分析工具：java-log-diagnoser
> 脚本结论：`chain_length=1`、`frame_count=0`、`has_business_frame=false`
> 降级原因：异常只有消息、没有任何堆栈帧（`at ...`），无法定位到代码行

## 1. 已知

- 异常：`java.lang.IllegalStateException: 库存扣减返回失败码 STOCK_LOCK_FAIL`（L3），**无堆栈**。
- 业务上下文：下单请求 `orderId=SO20261101033`（L1 接收、L2 失败），失败后由全局处理器转换为 HTTP 500
  （L4，`traceId=9c1e77`）。
- 时间特征：`[事实]` L1（09:11:58）到 L2（09:12:03）间隔约 5.3 秒，与常见的 RPC/DB 超时量级接近，
  但日志中**没有**任何超时异常，不能据此断言是超时。
- 可确认的是：抛出方在业务代码内（消息为中文业务文案），**不是**框架或 JVM 直接抛出的。

## 2. 为什么不够

`at` 帧缺失意味着无从得知：异常在哪个类哪个方法抛的、经过哪些调用、内层是否还有 `Caused by`。
仅凭一句业务文案，任何"根因"都只能是猜测，而猜测在这个场景下会直接误导排查方向
（例如去查库存服务的网络，而实际问题可能是本地校验逻辑把失败码当异常抛出）。
因此本报告**不输出根因假设，也不输出修复建议**。

1. **完整堆栈**：`orderId=SO20261101033` 或 `traceId=9c1e77` 对应的 ERROR 日志全段（含所有 `at` 与 `Caused by`）。

2. **`STOCK_LOCK_FAIL` 的来源**：这个字符串是库存服务返回的 code，还是本系统自定义的枚举？

## 5. 补充信息后我会怎么分析

拿到完整堆栈后，按以下顺序推进，不需要你再重复描述现象：

1. 用脚本重新抽取，确认主链与故障点；
2. 若最深 `Caused by` 是连接/超时类异常 → 转库存服务可用性与网络；

4. 若堆栈仍缺失 → 建议在抛异常处补 `log.error("...", e)`，保留原始异常而不是只打 `e.getMessage()`。
